- 日期：2026-10-05
- 定位：`benchmark/FUSE_PIPELINE_DEFECTS.md` F13 的**修复方向验证**——F13 已证"LLM 按下标对齐、
  跨语言语义对齐未发生"，且上限对照证明任务可解、瓶颈在本地容量。本报告验证替代路线：
  **多语言向量召回 + 单调 DP + 人工确认**，把 LLM 从对齐环节移除。
- 素材：用户已预校对的工程（`examples/benchmark_examples/`，本地留档不入库）
  - `moon_sisters.gsa`：有配音。game 轨 ASR 15 段（Canon/Sonnet/Aria）+ 主播轨 `mob` 59 段（按设计排除），
    语料 17 条，**GC 无碎片**
  - `glupov.gsa`：无配音。`embed_ocr` **22 段**（画面内嵌字幕 OCR，含 OCR 噪音），语料 34 条
  - 时间轴一律从事件取（融合不改时间轴）
- 运行时：`runtime/deps_embed`（onnxruntime 1.20.1 CPU + tokenizers，pip `--target`，复用项目既有约定）
  + `runtime/models/embed/multilingual-e5-small`（qint8，113MB）；**未引入 torch**、不占 GPU、不改产品默认 LLM

## 一、结论

**向量召回可以替代 LLM 完成跨语言对齐**，且质量远高于 3B/7B：

| 素材 | 段数 | 命中 | 单调性 | 未使用语料行 |
|---|---|---|---|---|
| moon（ASR，有配音） | 15 | **15/15** | 成立 | 2/17（该片段确实没说到） |
| glupov（嵌字，无配音） | 22 | **22/22** | 成立 | — |

逐段人工核对（报告 §三 摘要）显示映射**语义正确**，包括此前 LLM 处理不了的类型：
裸名字段（`Canon.` → `卡侬妹妹。`）、短句（`What she said.` → `就是就是！`）、
带 OCR 噪音的碎片（`ontinue tempering my will…` → `必须不断磨练自己的意志力…`）。

## 二、决定性方法学发现：**表头必须先剥离**

glupov 首次跑出 **3/22**（近乎全灭），诊断后确认**不是模型问题**：

- 每条语料以 `斯捷潘尼扬\n「缟玛瑙」\n` 开头、每条 GC 以 `Stepanyan\nOnyxAgate\n` 开头（**完全同形**）；
- 表头主导了句向量 → **任意配对**的余弦都挤在 0.735~0.833（GC[1] vs 语料 1..6 =
  0.768/0.758/0.766/0.740/0.735/0.752，几乎无区分度）；
- 正文的判别信息被**淹没**，模型只能给出"同说话人的近邻"，无法定位到具体某句。

**修复：编码前剥离前导表头行**（短行且无句末标点 → 名字/头衔/名牌）。效果可量化：

| 素材 | 可区分度（top1 − 语料中位） | 全矩阵 max | 命中 |
|---|---|---|---|
| glupov 带表头 | 0.032 | 0.833 | 3/22 |
| **glupov 剥表头** | **0.054** | **0.875** | **22/22** |
| moon 带表头 | 0.049 | 0.885 | 15/15 |
| **moon 剥表头** | **0.057** | **0.907** | 15/15 |

⇒ 这条与 F1/F2 的结论**同源**：语料/转写的"名字行"不是无关装饰，它会污染下游一切按语义工作的环节
（LLM 提取角色名 5/6 错、向量召回被淹没）。**"名字行剥离"是两条技术路线的共同前置**。

## 三、产品形态（建议）

```
① corpus 全量 → 剥表头 → E5 编码一次（向量库；语料变动时增量更新）
② 每条 GC → 剥表头 → 编码 → top-k 召回（k=3~5）        ← 语义对齐，无需 LLM
③ 单调 DP 修正（语料与转写同序 ⇒ 对齐必单调；lam≈0.02 抑制过度跳跃）
④ 一对多合并：同一语料行被多段命中 = 同句的多次显示/碎片（语义正确，非错误）
⑤ 低置信（score<0.78）或歧义（top1−top2<0.02）→ 待人工确认清单
⑥ 产出：替换后的 SRT（时间轴沿用转写段）+ 待确认清单
```

**重量代价**：deps_embed（onnxruntime CPU ~50MB）+ 模型 134MB ≈ **190MB**，对比 LLM 路线（3B=2GB 且要 GPU）。

## 四、与 LLM 路线的对比（同一素材、同一任务）

| 维度 | LLM（Qwen2.5-3B，现行） | 向量召回（E5-small qint8） |
|---|---|---|
| 跨语言语义对齐 | **未发生**（恒等映射，错序用例 0~3/12 = 随机） | 错序判别器 **84/84 (100%)**，MRR 1.000 |
| moon 真实素材 | 恒等映射，命中 17/30（算术巧合） | **15/15 正确** |
| glupov 真实素材 | 未测（无 ASR 曾跑不了） | **22/22 正确** |
| 抗干扰（148 条噪音池） | F12：编号体系崩坏 | recall@1 **12/12** |
| 运行成本 | 1.96GB + GPU，批级解析失败风险（F3） | 134MB，CPU，无解析环节 |
| 失败模式 | 静默降级为外语原文（F3/F4） | 低置信段进"待确认清单"，可解释 |

## 五、局限与未验

1. **glupov 无独立真值**：用户预校对工程未附对应关系，22/22 是"每段都找到单调唯一近邻且人工抽查合理"，
   需要你抽查确认（逐段表已落盘 `temp/bench_output/fuse_vec_glupov.json`）。
2. **moon 的 2 条未使用语料行**（`空月的航船…`/`属于遥远过去的回忆消散了…`）是否应有对应段，
   取决于该片段是否真的没出现这些台词——请你核对。
3. 阈值（0.78 / 0.02）是**初值**，应据你的抽查结果重定；k 取 3 已足够（top3 覆盖 100%）。
4. 未测：pierro（48min、148 条语料、含 51 条噪音行）——建议作为规模化验证的下一例。
5. 未接产品：本轮只做离线验证，**未改动 fuse 管线**（仍是上一轮的纯文本契约）。
   接入时的形态建议：向量召回作为"预处理 + 候选生成"，`fuse_pipeline` 改为消费候选，
   或直接把 LLM 调用换成"可选复核"。
