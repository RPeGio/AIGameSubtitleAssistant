## 二、决定性方法学发现：**表头必须先剥离**

glupov 首次跑出 **3/22**（近乎全灭），诊断后确认**不是模型问题**：

- 每条语料以 `斯捷潘尼扬\n「缟玛瑙」\n` 开头、每条 GC 以 `Stepanyan\nOnyxAgate\n` 开头（**完全同形**）；
- 表头主导了句向量 → **任意配对**的余弦都挤在 0.735~0.833（GC[1] vs 语料 1..6 =
  0.768/0.758/0.766/0.740/0.735/0.752，几乎无区分度）；
- 正文的判别信息被**淹没**，模型只能给出"同说话人的近邻"，无法定位到具体某句。

**修复：编码前剥离前导表头行**（短行且无句末标点 → 名字/头衔/名牌）。效果可量化：

| 素材 | 可区分度（top1 − 语料中位） | 全矩阵 max | 命中 |
|---|---|---|---|
| glupov 带表头 | 0.032 | 0.833 | 3/22 |
| **glupov 剥表头** | **0.054** | **0.875** | **22/22** |
| moon 带表头 | 0.049 | 0.885 | 15/15 |
| **moon 剥表头** | **0.057** | **0.907** | 15/15 |

> **作用域限定（2026-10-05 用户复核后修正）**：表头剥离**只作用于模型输入**（编码/检索），**产物文本必须保留表头原文**。首版实现把剥离后的正文直接写进了 SRT/JSON，用户指出后已修正：
> `split_header(text) -> (header, body)`，编码用 `body`，产物用 `header + body` 原文还原。
> 即「名字行」在产品侧仍是台词的一部分（是否最终输出由后续产品决策），只是**不参与语义匹配**。

⇒ 这条与 F1/F2 的结论**同源**：语料/转写的"名字行"不是无关装饰，它会污染下游一切按语义工作的环节
（LLM 提取角色名 5/6 错、向量召回被淹没）。**"名字行剥离"是两条技术路线的共同前置**。

### 2.1 用户复核发现的两处实现缺陷（均已修复）

1. **省略号条目被整段剥空**：语料第 30 条原为 `安东\n原「第九连队」临时连长`（正文只剩省略号，而省略号行当时缺失）→ `split_header` 逐行剥到无正文，该条变成空串，导致其后的语料行整体前移一位，表现为「GC[19]→OCR[18]、GC[20]→OCR[19]……GC[22] 回绕到 OCR[1]」。
   用户补齐省略号（`…`）后仍暴露出我的第二层缺陷（见下）。
   防护：`split_header` 在**剥到无正文时不再剥离**（返回 `(None, 原文)`），避免空串参与匹配。
2. **DP 单调性未真正强制**：状态转移里「无对应」分支沿用了 `argmax(dp[i-1])` 作为前驱，使匹配下标可回退/回绕（正是 GC[22]→OCR[1] 的来源）。已重写为「`dp[i][j]` = 前 i 段处理完且已用最大语料下标为 j」+ **严格递增**转移（`k > j`，跨行计 `skip_penalty`），回溯不再出现倒退或回绕。

修复后 glupov 命中序列为严格的 `1,2,…,15,28,…,34`（无位移、无回绕），GC[18] 正确落到省略号条目（OCR[30]）；用户已核实该对应关系。

## 三、产品形态（建议）

```
① corpus 全量 → **剥表头（强制）** → E5 编码一次（向量库；语料变动时增量更新）
② 每条 GC → 剥表头 → 编码 → top-k 召回（k=3~5）        ← 语义对齐，无需 LLM
③ 单调 DP 修正（语料与转写同序 ⇒ 对齐必单调；lam≈0.02 抑制过度跳跃）
④ 一对多合并：同一语料行被多段命中 = 同句的多次显示/碎片（语义正确，非错误）
⑤ 低置信（score<0.78）或歧义（top1−top2<0.02）→ 待人工确认清单
⑥ 产出：替换后的 SRT（时间轴沿用转写段）+ 待确认清单
```

**重量代价**：deps_embed（onnxruntime CPU ~50MB）+ 模型 134MB ≈ **190MB**，对比 LLM 路线（3B=2GB 且要 GPU）。

## 四、与 LLM 路线的对比（同一素材、同一任务）

| 维度 | LLM（Qwen2.5-3B，现行） | 向量召回（E5-small qint8） |
|---|---|---|
| 跨语言语义对齐 | **未发生**（恒等映射，错序用例 0~3/12 = 随机） | 错序判别器 **84/84 (100%)**，MRR 1.000 |
| moon 真实素材 | 恒等映射，命中 17/30（算术巧合） | **15/15 正确** |
| glupov 真实素材 | 未测（无 ASR 曾跑不了） | **22/22 正确** |
| 抗干扰（148 条噪音池） | F12：编号体系崩坏 | recall@1 **12/12** |
| 运行成本 | 1.96GB + GPU，批级解析失败风险（F3） | 134MB，CPU，无解析环节 |
| 失败模式 | 静默降级为外语原文（F3/F4） | 低置信段进"待确认清单"，可解释 |

## 五、局限与未验

1. **glupov 无独立真值**：用户预校对工程未附对应关系，22/22 是"每段都找到单调唯一近邻且人工抽查合理"，
   需要你抽查确认（逐段表已落盘 `temp/bench_output/fuse_vec_glupov.json`）。
2. ~~moon 的 2 条未使用语料行待核~~ → **已确认为预期行为**（用户核实）：这两句是**无配音的游戏内文本**，
   ASR 未识别到。同理 glupov 的 12 条未用语料行是**留给模型/召回的噪音容忍度素材**。
   判据澄清（用户）：**语料多出来是正常的，缺失才是不正常**——语料是「作品全集」，转写侧只是
   本次切片实际出现的那部分；因此「未使用语料行」不构成缺陷指标。
3. **阈值（0.78 / 0.02）是未经校准的初值**：正判据其实是 DP 的 `unmatched_penalty=0.25` / `skip_penalty=0.02`。歧义告警偏多（moon 6 段、glupov 15 段），主因是**同角色连续台词的相似度天然接近**（相邻语料行常差 0.005~0.02），按 margin 排序告警噪声大——建议改为「按 DP 全局约束后的置信度」或直接以 DP 结果为准、只用 margin 做**人工复核排序**。阈值须据你的抽查结果重定。
6. **产物语义待产品决策**：当前产物保留了语料原文的**表头行**（`斯捷潘尼扬\n「缟玛瑙」\n` 等）。是否在最终字幕中输出名字行（F1/F2 的同一问题）仍需你定；技术上「保留/剥离」已成可选项。
4. 未测：pierro（48min、148 条语料、含 51 条噪音行）——建议作为规模化验证的下一例。
5. 未接产品：本轮只做离线验证，**未改动 fuse 管线**（仍是上一轮的纯文本契约）。
   接入时的形态建议：向量召回作为"预处理 + 候选生成"，`fuse_pipeline` 改为消费候选，
   或直接把 LLM 调用换成"可选复核"。

## 五之补：由本验证导出的产品结论（用户决策，2026-10-05）

1. **产物文本必须与对应语料逐字一致**：语料带名字行则产物带，不带则不带。
   → 名字行剥离**只用于模型输入**（编码/检索），产物路径一律用语料原文（已实现并核验：
   两案例命中段的产物文本与语料条目**逐字相同**）。
2. **内嵌字幕 OCR 比 ASR 更具普适性**：内嵌字幕同时覆盖「有配音」与「无配音」两种场景，
   ASR 只覆盖有配音；moon 中 ASR 漏掉的正是无配音台词（片段中确有画面字幕但无人声）。
   → 对实况视频**直接 OCR 其内嵌字幕**，在文本覆盖面上优于 ASR 路线；
   这同时改变 F1「说话人契约」的定位：若以嵌字轴为主，说话人来源只能是画面名字框/人工标注，
   而非 ASR 说话人分离。
3. **「未使用语料行」不是缺陷指标**（见 §五-2 判据澄清）。
