### P2-3 `parse_reference` 对畸形时间码静默降级为正文

- **位置**：`common/mod.rs:247-258`
- **问题**：时间码行要求严格匹配 `" - "` 分隔（`split_timecode_line`）。若某行时间码打错（单个 `-`、多空格、3 段而非 4 段），该行不满足 `split_timecode_line`，会走到 `else if let Some((_, _, lines)) = cur.as_mut() { lines.push(t) }` —— **被当作上一条的文本追加**。参考文本是基准的"真值"，这种静默污染会让分数错得无声无息（与 P0-1 同类风险）。
- **修复建议**：若一行含 3 个 `:` 且含 `-` 却解析失败 → 直接 `Err`（附行号），不要并入正文。
- **状态**：✅ 已修复

### P2-4 流水线失败与"环境缺失"同样以跳过收场，基准可能空跑通过

- **位置**：`common/mod.rs:161-191`（`run_ocr` 出错即 `eprintln!("[跳过] …")` 并返回 `None`；调用方 `return`）
- **问题**：素材/环境缺失时跳过是合理设计，但**流水线自身报错**（例如某次改动让 OCR 在该案例上必失败）也走同一条路——测试打印跳过并**判定通过**。对一个用来防回归的质量基准而言，"失败看起来像跳过"是危险的假绿。
- **修复建议**：区分两类退出——环境/素材缺失 → 跳过；`run_ocr_pipeline` 返回 `Err` → `panic!`/断言失败（附带错误信息），让真实回归不被掩盖。
- **状态**：✅ 已修复
  - `common::run_ocr` 契约改为：**素材/环境缺失由调用方提前跳过**（`require_file` / `build_ocr_manager` 不变），走到它之后仍失败即流水线真实故障 → `expect`/`panic!` 并带上视频路径与错误，签名由 `Option<(…)>` 改为 `(…, f64)`。
  - 两个调用方（`bench_corpus.rs` / `bench_hardsub.rs`）去掉 `None => return` 分支。
  - 冒烟验证：glupov 语料重跑 **97.3**（与改前逐项一致），确认成功路径行为不变。
  - `benchmark/README.md` 补明该约定（"素材与环境齐备后流水线报错则测试失败"）。
